# Wheel Prizes — Open Questions

Вопросы заказчику (Косте), отложенные на следующую итерацию после закрытия технических багов.

Поднялись по результатам трёх параллельных аудитов фичи `feature/wheel-prizes` (UX + бизнес-логика + код-ревью) от 17.05.2026.

Эти вопросы влияют на бизнес-поведение и не могут быть решены разработчиком в одиночку. До получения ответов соответствующие участки кода остаются в текущем состоянии.

## Q1. Откатка спинов и промокода при отмене заказа

**Сценарий.** Клиент сделал заказ → начислились спины → клиент крутанул → выиграл легендарный приз → менеджер отменяет заказ.

**Что нужно решить.**
- (a) Списать спины обратно с баланса клиента?
- (b) Дезактивировать промокод-приз (поменять `active = 0`)?
- (c) Пересмотреть эпические пулы (вычесть прибыль клиента из `qualified_customers_json`)?
- (d) Не трогать ничего — оставить в пользу клиента?

**Сейчас.** Вариант (d) — никаких откатов. Создаёт фарм-эксплоит: можно сделать заказ, доставить, накрутить спины, отменить и оставить выигрыш.

**Где править после ответа.** `server/routes/crm-operations.js` — ветка `desiredStatus === 'cancelled'` (строки ~1232+). Нужен новый хук `revertWheelEffectsForOrder(orderId)` в `server/wheel/wheel-service.js`.

## Q2. Изменение состава заказа после доставки

**Сценарий.** Менеджер дописал товаров в уже доставленный заказ → `final_amount` вырос с 80 BYN до 120 BYN.

**Что нужно решить.** Должны ли начислиться доспины с дельты `+40 BYN`?

**Сейчас.** Нет — идемпотентность по `last_synced_order_id` сразу отфутболит повторный вызов. Менеджер не получает никакого сигнала, что состав поменялся.

**Где править после ответа.** `server/wheel/wheel-service.js:282-310`. Может быть привязка к новому полю `wheel_balance_ledger.amount` для дельт.

## Q3. Pity vs эпик одновременно

**Сценарий.** У клиента `consecutive_nothing = 3` (порог pity достигнут), и одновременно сработал эпический пул — клиент квалифицирован первым из N.

**Что нужно решить.**
- (a) Выдать только эпик, pity-счётчик сбросить (как сейчас)
- (b) Выдать pity-приз сейчас, эпик отложить на следующий спин
- (c) Выдать оба

**Сейчас.** Вариант (a). Эпик «съедает» гарантированный pity-приз, клиент получает что-то более ценное, но теряет «гарантированный обычный».

## Q4. Эпик с `max_total > 1`

**Сценарий.** На эпическом призе настроено `max_total = 3`. Первый эпик выдан, пул закрылся. Дальше: пул создаётся заново, когда новые клиенты пересекут порог.

**Что нужно решить.** Старые квалифицированные клиенты, не получившие приз, выпадают из системы. Намеренно?

**Сейчас.** Да, выпадают. После закрытия пула `qualified_customers_json` сохраняется как был, но в новом пуле учитывается только профит после `closed_at` старого. Если старые клиенты не сделают новые заказы — они никогда снова не попадут.

**Альтернатива.** Переносить `qualified_customers_json` старого пула в новый при пересоздании.

## Q5. Promo-template с `has_gift = 1` как шаблон рулетки

**Сценарий.** Менеджер использует промокод-подарок (с `has_gift = 1`) как шаблон для рулеточного приза. Рулетка генерит приз-промокод, который при применении в чекауте дополнительно вызывает «выдай физический подарок» в логике менеджера.

**Что нужно решить.** Запретить такие шаблоны? Или разрешить, но пометить в CRM явно?

**Сейчас.** Разрешено без пометок — менеджер может случайно настроить «бесконечный подарок» через рулетку.

**Где править после ответа.** Валидация в `createPrize`/`updatePrize` (`server/wheel/wheel-service.js:787-859`).

## Q6. Live-feed — opt-out для клиентов?

**Сценарий.** Имена и аватары клиентов выигравших призы показываются в бегущей строке всем посетителям рулетки. Это PII (имя + фото).

**Что нужно решить.**
- (a) Оставить как есть — открытый feed без opt-out
- (b) Добавить opt-out настройку в профиле клиента
- (c) Анонимизировать жёстче (только инициалы без аватара)

**Сейчас.** Вариант (a). По ТЗ заказчика opt-out не упомянут.

**Юридический контекст.** В РБ есть закон о персональных данных. Без согласия публиковать имя+фото — серая зона.

## Q7. Сумма для спина — `final_amount` (после скидок) или `total_amount` (до)?

**Сценарий.** Клиент сделал заказ на `total_amount = 100 BYN`, применил промокод на 20%, заплатил `final_amount = 80 BYN`. Сколько BYN засчитать к рулетке?

**Что нужно решить.**
- (a) `final_amount = 80 BYN` — спин начислится с того, что клиент реально заплатил
- (b) `total_amount = 100 BYN` — спин начислится с полной стоимости

**Сейчас.** Вариант (a) — `final_amount`. Это «честнее» для бизнеса (платим спины с реальной выручки), но менее щедро.

**Костя в переписке сказал «сумма заказа», без уточнения.** Нужно подтверждение.
