# Авторизация через пригласившего

## Поток клиента

- При первом входе новый клиент сразу видит обязательное окно авторизации.
- Закрыть или пропустить окно нельзя: каталог и цены доступны только после успеха.
- Авторизация выполняется через `POST /api/referral-authorization/authorize`, а
  `POST /api/orders` повторно защищает прямой обход API.
- Username проверяется только по локальной базе. Telegram `resolveUsername` здесь запрещён.
- После успеха клиент, доступ и связь с пригласившим сохраняются одной транзакцией.
- Первый заказ создаётся позже и дописывается в уже сохранённую связь.
- Отмена заказа не удаляет доступ и связь.

Переключатель `referral_authorization_enabled` хранится в `settings`. Начальное значение берётся из
`REFERRAL_AUTHORIZATION_ENABLED`, по умолчанию функция выключена.

## Кто может приглашать

Клиент найден в единственном числе по username, не удалён, не приглашает себя, имеет заказ
`completed` или `delivered`, не имеет действующей общей блокировки и отдельного запрета приглашать.
При совпадении нескольких старых username выбор не делается.

Во вкладке CRM «Клиенты → Авторизация» сотрудники ведут отдельный список запрещённых username
(например, аккаунтов администраторов). Список не требует наличия клиента в базе, сравнивается без
учёта регистра и проверяется до поиска пригласившего. Такой отказ не расходует попытку.

## Попытки

Состояние хранится в `referral_auth_states` по подписанному Telegram ID. Формат, неизвестный или
невыдававшийся пригласивший и приглашение себя расходуют попытку. Блокировка пригласившего,
запрет приглашать, неоднозначность и технические ошибки попытку не расходуют.

Третья ошибка создаёт бессрочную запись `customer_blocks` с типом `authorization_failed`.
Снятие этой блокировки сбрасывает счётчик до нуля.

## Данные

- `customers.access_authorized_at` и `access_authorization_source` — разрешение и его источник.
- `referral_auth_events` — неизменяемый журнал результатов.
- `customer_referrals` — постоянная связь по внутренним ID и снимок первоначального username.
- `customer_invite_bans` — история вечных запретов приглашать и их снятия.
- `referral_disallowed_inviter_usernames` — username, которые нельзя указывать как пригласивших.

При первой миграции источник `legacy` получают только клиенты хотя бы с одним выданным заказом (`completed` или `delivered`). Новые, собранные и отменённые заказы доступ не открывают. Остальные проходят авторизацию при входе. Повторная миграция не
разрешает доступ клиентам, созданным позднее после проваленной авторизации.

## Выпуск

1. Сделать резервную копию и прогнать миграцию на её копии.
2. Выложить совместимый сервер и интерфейс с выключенным переключателем.
3. Проверить обычный заказ.
4. Включать функцию отдельным запросом менеджера.

Отключение возвращает старый поток заказа и не удаляет накопленную историю.
